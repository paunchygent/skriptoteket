# ADR-0088: Cloudflare R2 Storage Boundary For Mina Filer And FileRefs

## Status

Proposed, updated after the HuleEdu File Service R2 contract slice validated
the shared service direction. This ADR records the Skriptoteket consumer
contract that must be reviewed before any production object-storage migration,
R2 credential sync, destructive cleanup, or runtime adapter rollout.

Implementation is blocked until `REV-PR-0411` approves the decision package and
every open question below is either answered in this ADR or moved into a named
follow-up decision with an explicit non-goal.

## Context

Skriptoteket currently stores reusable teacher files through `Mina filer`.
Metadata lives in PostgreSQL and file bytes are stored by `LocalVaultStorage`
under the configured vault root. The durable user-facing contract is `vault:*`
`FileRef` resolution, not local filesystem paths.

The current storage surfaces have different durability and ownership semantics:

- `VaultStorageProtocol` and `/api/v1/vault` own durable, user-scoped files.
- `SessionFileStorageProtocol` owns session-scoped uploads and staged files.
- Document Converter artifact and preview stores own app-local generated bytes.
- Runner artifact storage owns tool-run output staging.
- Sir Convert owns upstream conversion job artifacts and replay artifacts.

Cloudflare R2 is S3-compatible, but that does not make it a drop-in replacement
for every file path. The product decision is where identity, metadata, retention,
download/save semantics, and cross-product object ownership live.

HuleEdu now owns the validated shared File Service contract for object
lifecycle. Skriptoteket must consume that contract for `Mina filer` bytes
instead of creating a parallel direct-R2 control plane.

## Decision

Skriptoteket will migrate durable `Mina filer` bytes first. The `vault:*`
`FileRef` contract remains stable and the web/API layer must continue to expose
only protected Skriptoteket routes for list, save, restore, delete, and download.

`VaultStorageProtocol` remains the application boundary, but the implementation
path is now a HuleEdu File Service client adapter. Skriptoteket must not add a
direct R2 adapter for `Mina filer` in this migration tranche, and Skriptoteket
containers must not receive R2 bucket credentials.

Ownership is split as follows for v1:

- Skriptoteket owns `Mina filer` catalog authority: user-facing file records,
  display names, owner scoping, soft-delete/restore intent, picker eligibility,
  and list/browse responses.
- HuleEdu File Service owns object lifecycle: init, upload/finalize, canonical
  object metadata, checksum/size validation, download byte retrieval, and final
  object delete.
- HuleEdu File Service `list` is optional for v1. Skriptoteket browse/catalog
  must continue to use Skriptoteket-owned metadata until a later reviewed
  tranche explicitly moves catalog authority.
- Browser clients never receive direct R2 credentials, raw R2 object keys, or
  raw R2 URLs.
- HuleEdu Upload v2 essay, BOS, assessment, or batch semantics must not leak
  into Skriptoteket `Mina filer`. The shared surface consumed by Skriptoteket
  must be product-neutral and namespace-aware.

The preferred long-term architecture is one shared product-neutral File Service
for user-owned files across HuleEdu and Skriptoteket, with separate R2 buckets
or prefixes per product/runtime. The existing HuleEdu Upload v2 essay/batch
shape is not sufficient by itself for Skriptoteket `Mina filer`; it needs an
explicit product-neutral contract for object identity, metadata, reads, deletes,
retention, and migration.

Sir Convert job artifacts are not routed through Skriptoteket `Mina filer` or
the HuleEdu user-file service by default. Skriptoteket stores only explicit
teacher-saved outputs in `Mina filer`; upstream conversion artifacts remain
producer-owned until saved.

## Consequences

- The database remains the authority for Skriptoteket catalog state, while
  HuleEdu File Service is the authority for object lifecycle metadata. Local
  paths must not be the durable product identity.
- Skriptoteket catalog records must store an opaque File Service object
  reference plus enough mirrored content facts for UI and fail-closed checks:
  content type, size, SHA-256, File Service lifecycle state, and migration batch
  id where relevant. Bucket and object key values are infrastructure details and
  must not become domain concepts.
- `vault:*` refs must continue to be owner-scoped and fail closed for
  cross-owner, deleted, missing-object, or checksum-mismatched records.
- Document Converter saved-file batches must keep the PR-0404 contract: the
  browser submits ordered refs only, the server loads bytes by owner-scoped vault
  refs, and invalid refs fail the whole batch before conversion jobs are created.
- Protected download/save endpoints remain the filename, content-type, and
  authorization authority. Download bytes are fetched through HuleEdu File
  Service behind protected product routes; raw R2 object URLs must not leak to
  browser state, logs, or retained proof artifacts.
- Local development needs the HuleEdu File Service dev lane and signed product
  identity flow available before integration proof. A local filesystem fallback
  may remain only as rollback or pre-migration state, not as a second new object
  lifecycle authority.
- Production cutover needs a dry-run manifest, checksum proof, rollback plan,
  and explicit delete/lifecycle policy before any destructive action.

## Closed Decisions From HuleEdu Contract Alignment

1. The v1 `Mina filer` migration consumes HuleEdu File Service. It does not add
   a Skriptoteket direct R2 adapter.
2. Skriptoteket keeps catalog/list authority for v1.
3. HuleEdu File Service owns object lifecycle: init, finalize, canonical object
   metadata, download, and final object delete.
4. File Service list/browse is optional until a later reviewed tranche moves
   catalog authority.
5. Browser clients do not receive direct R2 credentials or raw R2 URLs.
6. HuleEdu Upload v2 essay, BOS, assessment, and batch semantics are forbidden
   in the Skriptoteket consumer contract.

## Remaining Open Questions

These questions are part of the decision contract. None may be left to
implementation without a named follow-up decision.

1. What exact File Service endpoints and request/response fields does the
   Skriptoteket client consume for init, finalize, metadata/head, download,
   delete, and checksum verification?
2. Which storage columns must be added to `user_vault_files`: File Service
   object reference, content type, size, SHA-256, lifecycle state, migration
   batch id, finalized timestamp, and delete/purge state?
3. How does Skriptoteket soft delete and restore map to File Service lifecycle:
   bytes retained during restore window, final purge calling File Service
   delete, and catalog state updated from File Service response?
4. What is the migration process: dry-run inventory, init/copy/finalize through
   File Service, checksum compare, dual-read, cutover, local rollback, and
   post-cutover cleanup?
5. Which surfaces migrate after `Mina filer`, if any: session files, Document
   Converter artifacts, previews, runner artifacts, or transcript blobs?
6. Which transient surfaces intentionally remain local filesystem storage?
7. How are File Service finalize success and Skriptoteket database-commit
   failure reconciled without orphaning objects or exposing missing records?
8. What exact live proof closes the migration: save, list, download, Document
    Converter saved-source batch, delete, restore, missing-object failure, and
    cross-owner denial?
9. What is the production `.env` sync order across Skriptoteket, HuleEdu, and
    Sir Convert, and how are secret names documented without committing values?
10. Which metrics, logs, and alerts prove File Service/R2 health without
    exposing object keys, tokens, signed URLs, or teacher file names?
